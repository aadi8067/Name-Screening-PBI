Assuming by “insurance factory” you mean an insurer’s operational processes—such as policy issuance, underwriting, claims and payments—a strong first Power BI project is a Claims Operations & Fraud Monitoring Dashboard.

What to build
Create a dashboard that helps an operations team answer

How many claims are arriving and being processed
How long do claims take to settle
Which claims are overdue or need attention
How much has been paid, and what remains outstanding
Are there unusual claims that should be reviewed
Useful KPIs
Claims received, open, closed and overdue
Average time from claim submission to settlement
Claims paid and outstanding amount
Claims handled per employee or team
Claims by product, region, channel and status
Percentage settled within the target service time
Potential fraud alerts for investigation—not a definitive fraud decision
Data you’ll need
For a realistic project, prepare these tables

Claims claim ID, policy ID, date reported, claim type, status, amount claimed, amount paid, handler
Policies policy ID, product, start date, customer ID, region
Customers customer ID and only the attributes needed for analysis
Payments payment ID, claim ID, date and amount
Claim events claim ID, event type, event time—for example, “received,” “assigned,” “approved”
Targets service-time targets by claim type or product
Use IDs to connect the tables. In Power BI, a simple star schema works well claims and payments as fact tables, with policies, customers, dates, products and regions as lookup tables.

Where to get data
Real insurer claim and policy data is generally internal and confidential, so you may not be able to obtain genuine company data for a portfolio project.

Good options are

Ask your company’s data or operations team for approved, anonymised extracts and confirm what you’re permitted to use.
Use public sample insurance data for a static prototype. Check its source and licence; many public datasets are historical, not real-time.
Create synthetic data for a demo. Generate claims, status changes and payments with timestamps, and label the data clearly as simulated.
For a portfolio project, synthetic data is often the safest option. You can simulate realistic claim events without exposing customer information.

How to make it real-time
Real-time data must arrive continuously from a source system; Power BI cannot make a static spreadsheet real-time by itself.

A typical architecture is

Claims system or event generator → streaming platform → Power BI

For a Microsoft-based setup, possible components include Azure Event Hubs or Microsoft Fabric Real-Time Intelligence for incoming events, with Power BI connected to the resulting data. Ask your organisation’s data platform team which services and licences are available. Product features and licensing can vary, so check your organisation’s current setup.

For a student or personal demo, create a small event generator that periodically sends simulated claim updates. If you only refresh a file or database every few minutes, describe it as near-real-time, not true real-time.

Suggested build steps
Choose a business question for example, “Which claims need attention today”
Define the audience claims manager, team lead or operations analyst.
Find or create the data begin with a small, clearly documented dataset.
Clean it in Power Query fix data types, remove duplicates and handle missing values.
Build the data model link claims to policy, date, product and region tables.
Create measures open claims, overdue claims, paid amount, average settlement time and service-level percentage.
Design report pages
Overview key KPIs and claim trends
Operations open, overdue and ageing claims by team or claim type
Payments claimed versus paid amounts
Claim detail a filtered table for authorised operational users
Add filters and drill-through date, product, region, claim status and channel.
Test the figures compare Power BI totals with the source data and ask a domain expert to validate the definitions.
Add streaming only after the basic report works test the end-to-end delay and show the last event time on the report.
Be careful with customer data use anonymised or synthetic records for development, restrict access to sensitive detail, and confirm that your design follows your organisation’s data-protection and access-control rules. A good first deliverable is a claims dashboard using synthetic data, followed by a real-time demo that streams simulated claim status updates.
